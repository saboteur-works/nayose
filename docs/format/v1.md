# Nayose vault file format — version 1

This document is the published, authoritative specification of Nayose vault
format version 1. It is written to be sufficient, on its own, for an
independent implementer — in any language, with no access to this project's
TypeScript source — to write a working reader (and, if desired, writer) for
this format.

**Never-overwrite policy.** Once published, `docs/format/v1.md` is never
edited or deleted, even to fix a mistake found later. Any change to the
format — including a clarification that changes reader behavior — ships as a
new version file (`docs/format/v2.md`, etc.) with its own `formatVersion`
value, never as an edit to this file. If you are reading this file and
believe it is wrong or incomplete, the fix is a new version document, not a
patch to this one.

---

## 1. The envelope

A vault file is a single UTF-8 encoded JSON text file. Its top-level JSON
value is always a JSON object (never an array, string, or other type) with
exactly three keys:

| Key            | Type                | Value                                                        |
|----------------|---------------------|---------------------------------------------------------------|
| `nayoseVault`  | string              | Always the exact literal string `"nayose-vault"`.             |
| `formatVersion`| integer             | Always the exact integer `1` for this document's version.     |
| `body`         | object              | The vault's contents (see below). Always a JSON object.       |

`nayoseVault` is the format's marker field: its presence with this exact
value is what identifies a file as a Nayose vault at all, as opposed to some
unrelated JSON file. A reader MUST check this field before trusting the file
in any way.

`formatVersion` is an integer, not a semantic-version string. See section 7
for the exact rule a reader must apply when checking it.

`body` currently has one meaningful key, `assertions` (see section 2). A
freshly created, empty vault has `body: {}` — the `assertions` key is
optional and its absence is equivalent to an empty array. A reader MUST
treat a missing `body.assertions` the same as an empty array, not as an
error.

No other top-level keys are defined for version 1. A reader should ignore
unrecognized keys inside `body` (to tolerate forward-compatible additions
within the same `formatVersion`) but MUST NOT ignore an unrecognized or
missing top-level marker or version field — those make the file
unreadable as a version-1 vault (see section 7).

### 1.1 Minimal example

```json
{
  "nayoseVault": "nayose-vault",
  "formatVersion": 1,
  "body": {}
}
```

This is a valid, empty vault: no entities, no assertions.

## 2. The assertion log

`body.assertions` is a JSON array of **assertion** objects. This array is
the vault's entire store of facts — there is no other data structure in the
file. Every entity, every field value, every relationship, and every
correction is represented as one entry in this array.

### 2.1 Assertion shape

Each element of `body.assertions` is a JSON object with exactly these keys:

| Key           | Type   | Meaning                                                                 |
|---------------|--------|--------------------------------------------------------------------------|
| `id`          | string | Unique identifier for this assertion. See "id values" below.            |
| `entityId`    | string | Opaque identifier of the entity this assertion is about.                |
| `fieldName`   | string | Opaque identifier of the field on that entity this assertion sets.      |
| `value`       | any    | The asserted value, stored and read back exactly as given.              |
| `actor`       | string | Opaque identifier of who/what made this assertion.                     |
| `timestamp`   | string | ISO 8601 timestamp of when the assertion was made.                     |
| `source`      | string | Opaque identifier of where this assertion came from.                   |
| `sourceClass` | string | Either `"registry-issued"` or `"user-asserted"`. See "sourceClass" below.|

**`id` values.** In this implementation's writer, ids are minted as the
decimal string representation of a monotonically increasing counter starting
at `1` (i.e. `"1"`, `"2"`, `"3"`, ...), scoped to a single vault file. A
reader MUST treat `id` as an opaque string for equality/lookup purposes
(e.g. to match `sourceAssertionId` or `overriddenRegistryAssertionId` — see
section 5) and MUST NOT assume it is numeric, sequential without gaps, or
comparable as an ordering signal. **Append order — the assertion's position
in the `assertions` array — is the only ordering signal this format
defines**, independent of what its `id` string happens to look like.

**`sourceClass`.** This is a closed, two-member enum. A conforming file's
every assertion has `sourceClass` equal to exactly one of:

- `"registry-issued"` — the fact came from an external authoritative
  registry (e.g. a PRO, a rights-registration body), not directly from a
  human user of this application.
- `"user-asserted"` — the fact was entered or corrected directly by a human
  user of this application.

No other string values are valid for `sourceClass`. A reader encountering
any other value has encountered a non-conforming file (this specification
does not define reader behavior in that case beyond: do not silently treat
it as either of the two known classes).

**`value`** is deliberately unconstrained JSON (string, number, boolean,
null, array, or object) — its shape depends entirely on `fieldName` by
convention (see sections 3 and 4). The log itself never inspects, coerces,
or transforms it: whatever JSON value was asserted is exactly the JSON value
a reader gets back.

### 2.2 Append-only, ordered semantics

`body.assertions` is a **strictly ordered list**, and that order matters as
much as the content of any individual assertion:

- The array's order **is** the order in which assertions were appended
  (oldest first, most recent last). This is a strict total order: for any
  two distinct assertions in the array, one is unambiguously "earlier" and
  the other "later," determined solely by array index, never by comparing
  `timestamp` strings, `id` values, or any other field.
- The log is **append-only**. There is no representation, anywhere in this
  format, of updating or deleting an assertion. Correcting a previously
  asserted fact is represented by **appending a new, later assertion** for
  the same `(entityId, fieldName)` pair — the old assertion remains in the
  array, at its original position, unchanged and undeleted, forever.
- Every place in this document that says "most recent" means: the
  assertion with the greatest array index among the assertions being
  considered. This is the ONLY definition of "most recent" used throughout
  this document, including in the projection rule (section 5).
- A reader that reorders, deduplicates, or drops assertions has produced a
  different file than the one on disk. A conforming reader MUST preserve
  and expose this order; it MUST NOT re-sort the array by `timestamp`, `id`,
  or any other heuristic before computing "most recent."

### 2.3 Assertion example

```json
{
  "id": "7",
  "entityId": "3f1b2c9e-...",
  "fieldName": "displayName",
  "value": "Jane Songwriter",
  "actor": "user:jane",
  "timestamp": "2026-03-14T10:22:00.000Z",
  "source": "manual-entry",
  "sourceClass": "user-asserted"
}
```

## 3. The entity model: the `$type`-assertion convention

This format has **no separate table, array, or index of "which entities
exist."** There is only the single flat `body.assertions` array described
above. An entity is not a row anywhere — it is a convention for how
assertions are used.

**An entity is identified purely by the presence, somewhere in
`body.assertions`, of at least one assertion whose `fieldName` is the exact
literal string `"$type"` and whose `entityId` is that entity's id.** The
`value` of that assertion names the entity's kind, as one of these six
literal strings:

- `"Party"`
- `"Account"`
- `"Work"`
- `"Recording"`
- `"Release"`
- `"Registration"`

There is no reserved or predictable format for `entityId` itself beyond "an
opaque string" — in this implementation's writer, entity ids are randomly
generated UUID strings (e.g. `"3f1b2c9e-4a11-4c2f-9e3a-1234567890ab"`), but a
reader MUST NOT parse or validate `entityId`'s internal structure. Treat it
as an opaque key.

**To reconstruct "which entities exist, and of what kind," a reader must
scan the entire `body.assertions` array and collect every distinct
`entityId` that has at least one `fieldName: "$type"` assertion.** If more
than one `$type` assertion exists for the same `entityId` (unusual, but not
forbidden by this format), the entity's kind for read purposes is the value
of the **most recent** such assertion (per the append-order definition in
section 2.2) — this is an ordinary application of the general
"most-recent-wins for a raw read" convention, not the full conflict-resolution
rule in section 5 (which is specifically about registry-vs-user disagreement
and does not apply to `$type`, since `$type` is not expected to ever be
`registry-issued` vs. `user-asserted` in conflict).

Every other fact about an entity — its display name, its title, its share
in a Work, its registration status, a Recording's parent Work, a Release's
member Recordings, and so on — is likewise just another assertion with that
same `entityId` and a `fieldName` naming the field. This implementation's
writer uses these well-known field names (a reader building an entity-model
layer, not just a raw log reader, will want to recognize them, though this
format does not forbid other field names from appearing):

| `fieldName`     | Used on kind(s)                 | `value` shape                                  |
|------------------|---------------------------------|-------------------------------------------------|
| `$type`          | all                              | one of the six entity-kind strings above         |
| `displayName`    | Party, Account                   | string                                           |
| `title`          | Work, Recording, Release          | string                                           |
| `workId`         | Recording, Registration           | string (the id of a `Work` entity)               |
| `recordingIds`   | Release                          | array of strings (ids of `Recording` entities)   |
| `registryName`   | Registration                     | string                                           |
| `status`         | Registration                     | one of `"registered"`, `"pending"`, `"unknown"`  |
| `share:{partyId}`| Work                             | Fraction object — see section 4                  |

A reader implementing only the format-level contract (this document) is
not required to recognize any of these field names to be conformant; they
are documented here because they are the concrete vocabulary the shipped
example in section 8 uses, and because an entity-model layer built on top
of a conforming reader will need them.

## 4. The `share:{partyId}` field-name convention

A Party's fractional ownership share in a Work is recorded as an assertion
**on the Work entity** (i.e. `entityId` is the Work's id, not the Party's
id) whose `fieldName` is constructed as:

```
share:{partyId}
```

That is: the exact seven-character literal prefix `share:` (the word
`share`, a colon, no space), immediately followed by the Party's `entityId`
string, with nothing else appended and no other separator. For example, if
a Party's id is `"a1b2c3"`, the field name asserted on the Work is exactly
the string `"share:a1b2c3"`.

Because `fieldName` is scanned for this exact prefix, an implementer wanting
to enumerate all shares recorded against a given Work must scan
`body.assertions` for every assertion whose `entityId` equals that Work's id
and whose `fieldName` starts with the literal string `share:`, then treat
everything after that prefix as the asserting Party's id.

A Work may have any number of Parties, each with its own independently
appended `share:{partyId}` assertion; a reader collects them by scanning,
exactly as with the `$type` convention — there is no separate "shares of
this work" list anywhere else in the file.

### 4.1 The Fraction value shape

The `value` of a `share:{partyId}` assertion is always a JSON object with
exactly these two keys:

```json
{
  "numerator": <integer>,
  "denominator": <integer>
}
```

Both `numerator` and `denominator` are JSON numbers (integers in practice).
No other keys are present on this object; no other representation (a
decimal number, a string like `"1/3"`, etc.) is used for a share value in
version 1.

**Fractions are stored exactly as asserted, unreduced.** For example, a
share may be legitimately recorded as `{"numerator": 2, "denominator": 6}`
even though it is mathematically equal to `1/3` — this format never reduces,
normalizes, validates, or otherwise transforms a Fraction value on write,
and a reader retrieving the raw assertion log must not assume it has been
reduced either. See section 6 for what a reader must do if it wants a
normalized, comparable, or summable view of shares.

## 5. The projection rule: deriving a field's "current" value

The raw assertion log (section 2) is the source of truth, but most
consumers do not want the full history of every field — they want a
single "current value" per `(entityId, fieldName)` pair, with any
registry-vs-user disagreement clearly marked. This section specifies,
precisely, how to derive that from the raw log. This rule is a pure,
read-only computation over the (already-ordered) list of assertions for one
`(entityId, fieldName)` pair — it never modifies the log.

### 5.1 Inputs

Given an `entityId` and a `fieldName`, first collect the **field history**:
every assertion in `body.assertions` whose `entityId` and `fieldName` both
match, **in their original append order** (do not re-sort). If this history
is empty, the field has no current value — stop; there is nothing to
project.

Split the field history into two sublists, preserving relative order within
each:

- `userAssertions` — every assertion in the history with
  `sourceClass == "user-asserted"`.
- `registryAssertions` — every assertion in the history with
  `sourceClass == "registry-issued"`.

Let `mostRecentRegistry` be the last element of `registryAssertions` (i.e.
the one with the greatest original array index among registry-issued
assertions for this field), or "none" if `registryAssertions` is empty.

### 5.2 Choosing the current value

1. **If `userAssertions` is non-empty**, the current value is the `value`
   of the **last** element of `userAssertions` (the most recently appended
   user-asserted assertion for this field). Call this assertion `current`.
   Its `sourceAssertionId`, `source`, and `sourceClass` for reporting
   purposes are `current.id`, `current.source`, and `current.sourceClass`
   (which will always be `"user-asserted"` in this branch).

2. **Otherwise, if `userAssertions` is empty but `registryAssertions` is
   non-empty**, the current value is `mostRecentRegistry.value`. Its
   reporting fields are `mostRecentRegistry.id`, `mostRecentRegistry.source`,
   and `mostRecentRegistry.sourceClass` (`"registry-issued"`).

3. **If both lists are empty** — impossible if the field history itself was
   non-empty, since every assertion's `sourceClass` is one of exactly these
   two values — this case cannot arise for a non-empty history.

Ties within a single `sourceClass` cannot occur: append order (array index)
is already a strict total order (section 2.2), so "the last element of a
list preserving that order" is always unambiguous.

### 5.3 The override marker

The override marker (`isOverride`) is computed **only in branch 1 above**
(i.e. only when the current value came from a user-asserted assertion). In
branch 2, `isOverride` is always `false` — there is no user assertion to
possibly disagree with a registry one, so there is nothing to override.

When in branch 1:

- If `mostRecentRegistry` is "none" (no registry-issued assertion exists at
  all for this field), `isOverride` is `false`.
- If `mostRecentRegistry` exists, compare its `value` to the current
  (user-asserted) `value` using **deep structural equality** (recursively:
  same JSON type, same primitive value or, for objects/arrays, same keys/
  elements each deeply equal — order-independent for object keys, order-
  dependent for array elements). If the two values are deeply equal,
  `isOverride` is `false`. If they differ by this comparison, `isOverride`
  is `true`.

**Important, non-obvious case:** if a user-asserted value happens to
structurally match the most recent registry-issued value exactly (e.g. a
user re-typed the same display name the registry already had), this is
**NOT** an override. `isOverride` is `false` in that case. "Override" means
"the current value disagrees with what the registry most recently said,"
not merely "a user assertion exists alongside a registry one." This
distinction is intentional: the marker exists to warn a downstream user that
two facts differ, and there is nothing to warn about when they agree.

Only the **most recent** registry-issued assertion is compared and cited as
"superseded," even if older registry-issued assertions also exist for the
field and also disagree with the current value — those older ones remain
retrievable via the full field history but are not individually reported by
this projection.

### 5.4 Projection output

A reader implementing this projection produces, per `(entityId, fieldName)`
pair with non-empty history, an object with these fields:

| Field                            | Present when         | Value                                                              |
|-----------------------------------|-----------------------|----------------------------------------------------------------------|
| `value`                           | always                | the current value, per 5.2                                          |
| `sourceAssertionId`                | always                | `id` of the assertion `value` was taken from                        |
| `source`                          | always                | `source` of the assertion `value` was taken from                    |
| `sourceClass`                     | always                | `sourceClass` of the assertion `value` was taken from                |
| `isOverride`                      | always                | boolean, per 5.3                                                     |
| `overriddenRegistryValue`          | only if `isOverride`  | `value` of `mostRecentRegistry`                                     |
| `overriddenRegistrySource`         | only if `isOverride`  | `source` of `mostRecentRegistry`                                     |
| `overriddenRegistryAssertionId`    | only if `isOverride`  | `id` of `mostRecentRegistry`                                        |

If the field has no assertions at all, there is no projection result for
it (represent this however is idiomatic in the reader's language — e.g.
`None`/`null`/absent key — this format does not mandate a specific "empty"
representation since it is outside the file itself).

### 5.5 Worked example of the projection rule

Given this field history for `(entityId: "work-1", fieldName: "title")`, in
append order:

1. `{id: "10", value: "Old Title", sourceClass: "registry-issued", source: "ascap", ...}`
2. `{id: "14", value: "New Title", sourceClass: "registry-issued", source: "ascap", ...}`
3. `{id: "22", value: "My Title", sourceClass: "user-asserted", source: "manual-entry", ...}`

- `userAssertions` = `[assertion 22]`. Non-empty, so branch 1 applies.
- `current` = assertion 22 (`value: "My Title"`).
- `registryAssertions` = `[assertion 10, assertion 14]`.
  `mostRecentRegistry` = assertion 14 (`value: "New Title"`).
- Compare `"My Title"` to `"New Title"`: not deeply equal → `isOverride = true`.
- Result:
  ```json
  {
    "value": "My Title",
    "sourceAssertionId": "22",
    "source": "manual-entry",
    "sourceClass": "user-asserted",
    "isOverride": true,
    "overriddenRegistryValue": "New Title",
    "overriddenRegistrySource": "ascap",
    "overriddenRegistryAssertionId": "14"
  }
  ```
  Note assertion 10 (`"Old Title"`) is NOT cited — only the most recent
  registry assertion is. It remains in the raw log and is retrievable by
  scanning full history, just not reported by this projection.

If instead assertion 22's value had been `"New Title"` (matching assertion
14 exactly), the result would have `isOverride: false` and no
`overriddenRegistry*` fields at all, even though a user-asserted assertion
still exists and is still what "wins" as current.

## 6. Share fractions: unreduced storage, read-time normalization

As stated in section 4.1, Fraction values (`{numerator, denominator}`,
whether stored as a `share:{partyId}` assertion's value or produced by
projecting one) are **always stored and returned exactly as asserted —
never automatically reduced, normalized, or validated** by anything in this
format or by the reference implementation's write path.

**Consequence for readers:** a reader that wants a normalized view of a
share — to display it in lowest terms, to compare two shares for equality,
or to sum multiple parties' shares in a Work to check they total to a whole
— MUST perform that reduction/normalization itself, at read time, on
whichever raw Fraction values it retrieves. This format does not guarantee,
and a reader must not assume, that any Fraction value already appears in
reduced form on disk.

The reference implementation's normalization rules (informative — not
required to reproduce byte-for-byte, but documented here so an
implementer's own read-time math can be checked against it):

- **Reduction to lowest terms:** divide both `numerator` and `denominator`
  by their greatest common divisor (GCD). A `numerator` of `0` reduces to
  `{numerator: 0, denominator: 1}`. Sign is normalized onto the numerator
  (i.e. a negative `denominator` is not produced by reduction).
- **Summation of multiple fractions:** compute a common denominator via
  least common multiple (LCM) across all the fractions being summed, scale
  each numerator accordingly, sum the scaled numerators, then reduce the
  result as above.
- **Equality comparison:** reduce both fractions to lowest terms first, then
  compare `numerator` and `denominator` pairwise (e.g. `1/3` and `2/6`
  compare equal after reduction).

### 6.1 Worked example

Two Parties hold shares in the same Work, asserted unreduced:

- Party `p-1`: `share:p-1` = `{"numerator": 2, "denominator": 6}`
- Party `p-2`: `share:p-2` = `{"numerator": 2, "denominator": 3}`

Neither is stored reduced. A reader computing the current total:

- Reduce `p-1`'s share: GCD(2, 6) = 2 → `{numerator: 1, denominator: 3}`.
- `p-2`'s share is already in lowest terms: `{numerator: 2, denominator: 3}`.
- Sum via LCM: common denominator of 6 and 3 is 6.
  `p-1` scaled: `2/6` (unchanged, already denominator 6 in original form —
  or equivalently `1/3 -> 2/6`). `p-2` scaled: `4/6`. Sum: `6/6`.
  Reduced: `{numerator: 1, denominator: 1}` — the shares total to a whole.

A reader must not conclude "these shares are complete/whole" by inspecting
the raw stored numerators/denominators directly (`2/6` and `2/3` do not
visibly "look like" they sum to 1 without this reduction step).

## 7. Version checking: exact match, refuse otherwise

`formatVersion` in the envelope (section 1) is a single integer, not a
semantic-version string, and this format does not define any notion of
backward- or forward-compatibility between different `formatVersion`
values.

A reader supporting version 1 of this format MUST check `formatVersion` for
**exact equality to the integer `1`**. If `formatVersion` is present but
not exactly `1` (whether it is `2`, `0`, `1.0`, `"1"` as a string, or any
other value), the reader MUST refuse to read the file as a version-1 vault.
"Refuse" means: stop, and report to the caller/user that the file declares
an unsupported format version (including the declared value, so the
consumer knows what it actually is) — the reader MUST NOT attempt a
best-effort read of an unrecognized version, MUST NOT silently coerce or
truncate the value to treat it as `1`, and MUST NOT guess at how a
differently-versioned body might be shaped.

This is a strict, exact-integer-match check, not a range check, not a
semver-style "compatible with ^1.0.0" check, and not a "greater than or
equal to" check. A file declaring `formatVersion: 2` is exactly as
unreadable to a version-1-only reader as one declaring `formatVersion: 0` or
omitting the field entirely — all three are refused identically, distinct
only in the diagnostic message.

If a later version of this format is published (e.g. as `docs/format/v2.md`
with `formatVersion: 2`), a reader wishing to support both versions checks
`formatVersion` against its own known set of supported integers and
dispatches to the correct version-specific reading logic per value — it
still never attempts to read an unrecognized value with best-effort
guessing.

## 8. Full worked example

- A Party (`p-1`, "Jane Songwriter") with a plain `displayName` field.
- A second Party (`p-2`, "Sam Composer").
- A Work (`w-1`, "Sunrise Song") whose `title` was set by a registry, then
  overridden by a user to a different title (a user-override-of-registry
  conflict case).
- Unreduced share fractions on the Work: `p-1` holds `1/3` (stored exactly
  as `1/3`) and `p-2` holds `2/3` (stored exactly as `2/3`) — summing to a

- **Entities found by scanning for `$type`:** `p-1` (Party), `p-2` (Party),
